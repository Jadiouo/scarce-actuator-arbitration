## 2. 閘門的混淆與事後診斷（探索性）

**問題**：REQ-S1-10 的 detected 只看 D = G_RL^V − G_HW^V。如果 RL 在沒有漏洞的基礎 M3C 上本來就勝過手寫最佳，那麼 RL 即使沒有利用漏洞，也會被判「找回」。

**D2 證實了這點**：Q=1100 與 Q=1700 兩格的 checkpoint md5 相同，數字全同。接線正確（參考策略 d2_parole 的結果會隨 Q 改變），但 RL 與 HW dz=0.3 在暫停期間一直報 v > EPS_REP，parole 從不觸發（最大平靜連續輪數：RL 0、HW 3；Q≥1100、L=2500）。

- 10 格在 V 下的 val 數字與正式評估的 val 結果逐位一致（sanity match）。

**解讀**
- **E>0 的意思**：策略的得利依賴漏洞環境。它不證明 RL 用的就是設計者預期的那條機制路徑，只證明得利與漏洞有關。
- **O1（兩種大小）、D1 s0.01**：val 上 D_val 幾乎全部由 E 構成，D^off 的點估計約為 0。但 D^off 的 CI 上界可到 +0.005 至 +0.009，與 D（+0.011 至 +0.017）同數量級，所以**不能排除部分 D 來自基礎優勢**。比較準確的說法是：detected 主要由漏洞利用驅動，基礎優勢的點估計很小。另外，HW^off 在同一組 seeds 上選出，會讓 D^off 偏低。
- **D1 s0.02**：E 很大（+0.166），策略在基礎 M3C 上 G 為 −0.114。它對漏洞高度特化，D 不可能來自基礎優勢。
- **D2（兩種大小）**：同一個 checkpoint，E 恰為 0，D 完全等於 D^off。**偵測規則在 E=0 時仍判定 detected，這是一個偽陽性**，不是「沒有資訊」。RL 沒有找到「暫停期間保持沉默」這條路徑。
- **O5（盲區）**：E ≈ 0（CI 含 0），RL 沒有利用這個盲區，符合規格「預期不被找到」。但偵測規則仍判 detected，這是第二個偽陽性。兩件事都要報告。
- **族內 O2、O3、D4**：RL 從漏洞得到的 E（+0.32 至 +0.47）**大於** HW 從漏洞得到的 ΔHW（+0.20 至 +0.27）。D<0 的原因是這些 RL 策略在基礎 M3C 上表現很差（G^off 為 −0.12 至 −0.18），HW 在基礎 M3C 上則有 +0.024。換句話說，RL 對漏洞利用得更多，但為此犧牲了基礎表現，總分仍輸給 HW。
- **以「有利用證據」重算，族外為 2/3（D1、O1）**，低於登錄的 3/3 門檻。正式閘門照登記為通過；若以利用證據為準，閘門不會通過。兩種說法都要報告，判定仍以登記規則為準（REQ-S1-17、N1）。

## 3. 基礎優勢與主實驗（旁證，不得當結論）

D2 與 O5 的策略沒有利用漏洞，在基礎 M3C 上 D^off 為 +0.008 至 +0.012，CI 都不含 0（val 與 val2）。這暗示 RL 類別在基礎機制上可能勝過手寫最佳，也就是主實驗 Q-main 的問題。但有三點限制：這些策略是在漏洞環境中訓練、用 val 選出的；HW^off 與 RL 在同一組 seeds 上比較；每格只有 1 個 run。主實驗的答案要看主實驗本身的 test 結果。如果主實驗得到 J3，S1 的檢測力說法要同時寫明本節的混淆：S1 的 detected 至少有 2 格是由同一種基礎優勢產生的。

## 5. 揭露

- **REQ-STOP-06 的 9 項**：D1 混合參考策略、誠實基準漂移、D4 knob 不單調、倖存者偏誤、designer_1 受汙染、盲區只有 O5、細網格使比較對 RL 保守、val2 用於校準、n_S≈565 不涵蓋與 burst 時鐘。最終報告須逐項列出，數字由腳本自 `vuln_suite.json` 與 `s1.json` 填入（REQ-STOP-05）；本文件不手填。
- **test seeds 提前使用**：見本文開頭。評估程式的數值部分在提前使用之後沒有改動：`git log b0f3b0a..HEAD -- arbitration/rl/s1_eval.py arbitration/rl/final_eval.py scripts/d2_s1_eval.py` 為空。
- **統計**：CI 只反映 seed 變異。每格只有 1 個 run，沒有 run 間變異。
- **診斷的 seeds**：val 已用於 checkpoint 選取，RL 的 val 數字偏高；val2 用於 knob 校準（不用於 checkpoint 選取）。D^off 是在 val／val2 量的，D 是在 test 量的，兩者不是同一組 seeds。
- **HW^off** 在被評估的同一組 seeds 上選出，對 HW 偏樂觀，因此 D^off 偏低。
- **D2 parole 計數**：腳本為 `scripts/diag_d2_parole_count.py`（從 .scratch 複製，CPU、seeds 0–3、T=20000、monkeypatch `_ExtD2.release` 計數）。這是我們自己的小樣本檢查，不是登錄分析。
- 診斷 JSON 的 git_sha（a0136d5）沒有記錄工作樹是否乾淨。學校工作樹當時只有未追蹤的舊 `results/direction2/runlogs/` 與輸出檔本身。
