# 機制變異漏洞：格式要求（盲設計者用）

本文件只規定「一個漏洞要怎麼描述」，不含任何關於檢測工具的資訊。設計者只需熟悉 M3C 在 arbitration/gpu/frontier.py 中的實作與模擬時序。

## 1. 變異的形式

- 漏洞是對 M3C 的一個「機制變異」：在原實作的某個 hook 或條件上做局部改動（改一個條件、一個常數、一條更新規則，或在某個時點加一個 hook）。
- 用可實作的虛擬碼描述，並明確指出改動發生在 frontier.py 中 M3C 的哪個位置（函式、步驟、變數名）。
- 變異只能依賴環境內部本來就有的量（機制自己的狀態、輪次、型別等）；不得改動 agent 的效用、型別分布或其他與審計無關的環境部分。
- 同一批漏洞的機制要彼此不同；每個漏洞各自獨立描述。

## 2. 大小旋鈕（knob）

- 每個漏洞必須有一個純量旋鈕 knob，單調控制漏洞的強弱（說明旋鈕越大或越小越強）。
- 必須明列「恆等值」：knob 取該值時，變異後的機制與原機制在輸出上逐位元相同（含隨機數消耗順序）。若恆等值不是 0（例如 ∞），須明寫。
- 說明旋鈕的合理範圍與離散化方式（連續或整數）。
- 恆等性要能被實際檢查：給出一句話說明為何恆等值時不會改變任何分支或亂數抽取。

## 3. 利用策略

- 必須附一個利用策略，證明漏洞確實可被占便宜。
- 策略只能使用 agent 自身可觀察量：自己的型別、自己的回報（報了什麼）、自己是否得標、自己是否被暫停（以及由暫停長度可得知的資訊）。
- 不得假設 agent 能看到機制的內部狀態（累積統計量、稽核是否發生、他人的私有資訊等）。
- 用文字或虛擬碼描述，必須足夠明確到能被直接實作。

## 4. 預期得利與旋鈕的關係

- 給出預期得利（相對於不利用漏洞時）如何隨 knob 變化的推論，例如單調性、近似比例、飽和或門檻行為。
- 一律標註「推論」；若有簡單的解析估算，附上推導的關鍵步驟。
- 說明得利在 knob 為恆等值時為零。

## 5. 輸出檔欄位格式

每個漏洞一節，依序包含下列欄位，欄位名稱固定：

1. `名稱`：簡短識別字串。
2. `變異定義`：改動位置與虛擬碼。
3. `旋鈕`：名稱、恆等值、強弱方向、範圍。
4. `利用策略`：僅用自身可觀察量的描述或虛擬碼。
5. `預期得利`：與旋鈕的關係（標「推論」）。

另在檔案開頭用一小段說明整批漏洞各自對應的機制環節，確認彼此不重複。
